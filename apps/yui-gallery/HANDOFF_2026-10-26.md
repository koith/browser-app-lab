# 심유이(Yui / 심혜성) 화보 아카이빙 프로젝트 — 개발 인수인계서

> 기준일: 2026-10-26 (KST) | 저장소: https://github.com/koith/browser-app-lab | 기준 브랜치: main
> 목적: 다음 개발 대화·담당자가 지금까지의 실제 산출물과 미완료 작업을 정확히 이어받아, 화보 원본 중심의 자동 아카이빙 시스템을 완성하도록 한다.

## 인수인계 핵심 — 새 개발 대화에서 가장 먼저 읽을 사항

> **2026-10-26 21:37 KST 재확인:** 이 문서는 실제 GitHub `main`에 보관된다. 채팅 메시지를 임시 인수인계서로 쓰지 말 것. 새 담당자는 이 파일을 먼저 읽고 작업 시작 전에 `main`과 GitHub Actions 로그의 **현재 상태**를 다시 조회한다.

**업무 범위와 우선순위**

- 이 작업의 최종 목표는 **심유이(Yui/심혜성)의 화보 작품들을 가능한 한 많이, 작품당 최대한 높은 실제 해상도의 사진 파일로 확보하여 무료 대용량 온라인 저장소에 보관하고, 동일 파일을 온라인 갤러리에서 직접 열람/개별·앨범별 다운로드하도록 연결하는 것**이다.
- 공개 SNS 게시물 445장, 중국 사이트 화보 목록/썸네일, Google Drive 빈 폴더, 자동화 스크립트 개수는 화보 아카이빙 완료 수치에 넣지 않는다.
- 현재 재현 가능한 공개 **웹 화보 5개, 합계 405장**은 영구 외부 저장소에 업로드된 상태가 아니다. **프로젝트 완료 아님.**
- **TinyFish 사용하지 말 것.** Chrome/Playwright, 직접 HTML/HTTP, gallery-dl, Scrapy, GitHub Actions의 사용자 승인 범위에서 구현.
- **저장소 미확정:** TeraBox 무료 용량은 유망하지만 비공식 rclone 연결·세션 만료·속도·무료 정책의 장기 안정성이 미검증이다. 특정 제공업체를 '문제없다' 또는 '이미 연결됨'이라고 말하지 말 것.

**첫 개발 세션에서 즉시 수행하는 작업**

1. `main` 최신 커밋과 `.github/workflows/yui-four-public-albums.yml`, `yui-verified-public-album.yml`, `yui-cloud-real-albums-dryrun.yml`, `yui-cloud-integration-qa.yml`의 **최신 실행 SHA / 결과 / 산출물 만료 여부**를 재조회한다. 문서에 적힌 과거 성공 로그만으로 현재 성공을 추정하지 않는다.
2. 저장소의 `apps/yui-gallery/cloud/ingest_verified_zips.py`를 사용해 5개 화보의 실제 웹판 405장을 재수집·해시 대조하고, `originals/`, `previews/`, `metadata/catalog.json`을 만들어 405장/5작품을 검증한다. 이때 사진을 '발행사 초고해상도 원본'으로 허위 표시하지 않는다.
3. 클라우드 선택은 계정 연결에 필요한 **한 번의 사용자 승인**만 받고 시험한다. 먼저 작은 앨범 업로드 → 원격 목록 및 바이트 재다운로드·해시 검증 → iPhone 갤러리 열람 순서로 검증한다. 비밀번호/로그인 쿠키를 채팅이나 공용 저장소에 절대 넣지 않는다.
4. 저장소 연결 실패 시 해당 실패를 기록하고 실제 무료 대용량 대안(MEGA, TeraBox, Telegram, 사용자 소유 저장소)을 **업로드 API·자동화·원격 검증·용량·유지보수** 관점에서 시험한다. 검증 없이 다른 서비스로 갈아타거나 빈 껍데기를 출시하지 않는다.
5. 그 후 중국 화보 사이트별 **전체 작품 상세 페이지 발견 → 다음 페이지/무한 스크롤 끝까지 → 가능한 실제 최고 해상도 선택 → 파일별 해시와 해상도 검증 → 클라우드 업로드 → 온라인 갤러리 수락 테스트** 순서로 범위를 확장한다. 사이트별 중복, AI 보정본, 발행사 원본을 구분한다.

**현재 온라인 화면 두 개의 차이**

- [기존 공개 갤러리](https://koith.github.io/browser-app-lab/apps/yui-gallery/) : 일부 실제 공개 미리보기 26장 + 많은 링크/목록. 405장 영구 클라우드와 통합되지 않았다.
- [신규 클라우드 갤러리](https://koith.github.io/browser-app-lab/apps/yui-gallery/cloud.html) : 실제 클라우드 카탈로그를 읽는 화면과 인증 코드가 존재하지만, **TeraBox 계정 미연결·게이트웨이 미배포이므로 실사용 불가**. 모의 테스트 성공을 실서비스 성공으로 취급하지 않는다.

**다음 담당자 수락보고 필수 표기:** `화보명 | 원발행사 | 전체 표기 장수 | 실제 저장 장수 | 실제 파일 해상도 범위 | 원본/공개 웹판/AI 보정 여부 | 보관 제공자·실물 경로 | 원격 재다운로드 SHA256 | iPhone 실제 열람 QA | 미완료 이유`. **405장을 갤러리 화면에서 확인할 수 없다면 '통합 완료'라고 하지 말 것.**

## 1. 최우선 요구사항 (사용자 지시 — 절대 변경 금지)

1. 심유이/심혜성/Yui/沈惠星 등 예명과 중국어 표기를 통합 검색하여 **화보 작품 전체**를 찾아야 한다. 개인 SNS 이미지 수집은 별개 작업이며 화보 성과로 계산하지 않는다.
2. 각 화보의 상세 페이지를 방문하여 2·3페이지 및 마지막 페이지, 지연 로딩, 무한 스크롤, srcset/data-full/원본 이미지 연결까지 확인한다. 썸네일 몇 장이나 링크 목록만 확보한 것을 수집 완료라고 하지 않는다.
3. 가능하면 **발행사 원본 수준 초고해상도**를 확보하고, 공개 웹판만 가능하면 해당 픽셀 해상도와 품질 등급을 사실대로 표시한다. 인위적 업스케일을 원본으로 표시하지 않는다.
4. 저장소는 무료·대용량·관리 편의·자동 업로드·모바일 갤러리·개별 및 앨범 통째 다운로드를 모두 검증한 뒤 선택한다. 연결된 **실제 이미지 파일**을 온라인 갤러리가 직접 보여줘야 한다.
5. 사이트별 / 작품별 / 이미지별 폴더·인덱스 관리, 날짜순·이름순 정렬, 자동 신규 화보 감시·증분 수집·중복 방지·파일 무결성·중단 후 재개가 필요하다.
6. **TinyFish 의존 금지.** 다른 도구나 직접 HTTP, Playwright, gallery-dl, Scrapy, GitHub Actions를 우선 사용하며 정말 필수인 상황에서만 사유와 비용을 검토한다.
7. 사용자에게 미검증 사이트나 빈 폴더를 열어보라고 넘기지 말 것. 자동 QA와 실제 파일 열람을 마친 결과물만 완료로 보고한다. 기술 오류는 원인 파악·수정·재실행으로 해결한다.
8. 유료 화보도 목록에서 제외하지 않고 정식 구매·권한 있는 다운로드·원발행사 원본 경로를 조사한다. 무단 재게시 사이트의 존재는 의심할 수 있지만, 출처 불명이 곧 자유 복제·재배포 허락을 뜻하지는 않는다. 접근 제어 우회 또는 유료 원본 무단 복제는 진행하지 않는다.

## 4. 클라우드 결정 — 제안과 실제 연결을 구분

후보 A: **TeraBox 1TB 표방 무료 저장소**. 현재 소스는 이를 대상으로 작성됐으나 선택 확정/실계정 인증은 하지 않았다. 공식 요금의 1024GB는 기간 한정일 수 있으며 무료 계정에서 파일당 4GB 제한이 있다. 연동은 비공식 rclone-extra 기반으로 세션 쿠키에 의존한다. API 변경·로그인 세션 만료·제한·보안/성능/속도 리스크가 있어 완성 시스템으로 단정하면 안 된다.
후보 B: **MEGA 무료 20GB**. rclone 공식 지원으로 연결은 더 일관적이나 대용량 화보 수백~수천 세트에는 부족하다.
후보 C: **Cloudflare R2**. 이미지 게이트웨이·원본 다운로드 연동에 적합하나 무료 저장은 10GB-month 수준, 초과 과금이 발생한다. 사용자 동의 없는 유료 자원 생성 금지.
후보 D: **Telegram 개인 파일 저장**. 메시지 기반 파일 보관은 가능하지만 장기 대량 파일 인덱스, 자동 업로드·안정적 사진 갤러리 구현에 별도 API와 유지보수가 필요하다. 성공을 보장하지 않는다.

**저장소 선택 결론: 아직 검증 완료된 무료·대용량·자동 갤러리 저장소 없음.** 현재 TeraBox는 구현 후보일 뿐이며, 안전하고 재현 가능한 계정 인증과 업로드·원격 재다운로드 검증을 통과해야 최종 결정한다. 문제가 크면 공식 API가 있는 대안 또는 사용자 소유 NAS를 비교한다.

사용자 이메일/서비스 계정은 전혀 확정되지 않았다. 기존 Gmail, Render workspace, 카드, 저장소 계정 등을 임의 선택하지 말 것. 로그인은 본인 승인·보안 절차로만 진행. 비밀번호나 TeraBox ndus 쿠키를 대화창·공개 GitHub에 남기지 않는다.

### 클라우드 연동과 현재 가동 상태

- 시크릿(아직 없음): GitHub Actions secrets.YUI_TERABOX_NDUS, 환경변수 RCLONE_CONFIG_ARCHIVE_COOKIE, GALLERY_ACCESS_TOKEN.
- 게이트웨이 실행: Render 등 사용자 승인된 호스팅. 아직 실서비스 미배포·미연결.
- 클라우드 QA 실행 성공은 **가짜 테스트 이미지 3개/모의 API**를 통한 코드 검증이지 TeraBox 업로드 성공이 아니다.
- Render 무료 서비스는 유휴 시 정지될 수 있으며 재기동 지연이 있다. 원본 사진 저장 서버로 Render의 임시 디스크를 쓰지 말 것.
- 업로드 및 갤러리 연결 시 실제 다운로드된 원본 bytes의 SHA256 일치 여부까지 검증. 원격 rclone size-only check만으로 완전 무결성을 보장한다고 주장하지 말 것.

## 5. 다음 담당자의 개발 순서 (우선순위)

**P0 — 이미 확보한 405장으로 실제 운영 가능한 저장소/갤러리 1회 완주**
1. 소스 main과 위 문서 검토 후 공개 웹 이미지 405장 ZIP 재생성 또는 기존 비공개 Actions artifacts 획득. Actions 아티팩트는 만료될 수 있으니 영구보관으로 착각 금지.
2. cloud ingest로 사진 405개를 실제 파일로 스테이징, 썸네일 생성 및 SHA256·픽셀 크기 검증. dryrun의 기대 파일 집합과 비교.
3. 저장소 후보를 결정하려면 **작은 테스트 앨범 1세트를 사용자 승인 계정으로 올리고**, 원격에서 같은 바이트를 다시 다운로드한다. 속도, API, 용량, 세션 만료, 무료조건, iPhone 사용성을 실제 검증한다.
4. 게이트웨이와 cloud.html을 실서비스로 연결한 뒤 휴대폰으로 1개→전체 앨범 탐색·원본 저장 테스트. **405개 실파일과 0개 외부 링크를 구별해 표시**한다.
5. 실계정 접속 실패면 그 원인을 코드/권한/계정/플랜별로 분석하고 대체 API·서비스를 비교. 사용자에게 빈 스텁을 완성품으로 전달하지 않는다.

**P1 — 화보 아카이빙 대상의 실질적 확대**
1. 원발행사/시리즈별 작품 원장 생성 (SWEETBOX, ArtGravia, MOVIE FANTASY, BCUT 등 실제 확인된 자료만). 중국어 별칭의 오인/타 모델/중복 묶음을 구분.
2. 사이트 전체에서 작품 상세 링크를 자동 발견, 각 상세 링크의 모든 페이지/무한 스크롤/지연 로딩을 순회. 확장자는 img[src], picture[srcset], data-full, zoom anchor, 네트워크 image response 등을 실제 확인.
3. 화보 원장에 published_date, site_uploaded_date, claimed_count, discovered_public_count, downloaded_count, rights_access_type, quality_max_pixels, missing_count, source_provenance 기록.
4. 공개 미리보기와 정당하게 접근 가능한 원본 다운로드 분리. 같은 작품의 여러 웹판/AI 보정본을 원본과 섞지 말 것.
5. 전체 시퀀스가 공개된 곳에서는 **97/97 등 기대 장수 대조 후** 해시/디코딩/ZIP QA 통과시 완료. 반쪽 수집이면 PARTIAL.

**P2 — 운영 안정화**
1. 저장소의 실제 파일들로부터 갤러리 목록을 빌드하고 이름/날짜순(이미지와 앨범 개별), 출처·시리즈별 검색 및 다운로드, 폴더/카탈로그 내보내기 제공.
2. 신규 화보 정기 검색 + 기존 다운로드 아카이브 대조(증분), 기존 파일 재수집 방지, 실패 재시도, 404 감지, 보관소 용량·중복률 리포트.
3. 전체 ZIP 자동 생성, 장기 보존용 독립 백업 확보. 저장소 다운타임/세션 만료/정책 변경에 대비.
4. iOS Safari·Chrome, 데스크톱, 느린 네트워크에서 이미지 실제 로딩·확대·다운로드 자동 검증. 단순 DOM 개수/문법 통과로 완료 금지.

## 6. 수락 조건 (이 6개가 모두 충족되어야 최종 완료)

1. 실제 소유·승인된 대용량 저장소에 파일이 있고, 원격 재다운로드한 파일의 해시가 원본과 같다.
2. 대표적인 100장 이상 화보 최소 1개를 전체 장수, 개별 이미지 원본 파일, 다운로드, 보관까지 100% 연결 성공.
3. 사이트별·작품별 중복 해소 및 원 발행처/화보 제목/날짜/품질/실보관 장수/누락 장수 확인 가능.
4. 사용자 온라인 갤러리가 저장소에서 이미지를 직접 열고, iPhone에서도 크게 보기·이름/날짜순·개별/일괄 원본 저장이 정상 작동.
5. 자동 신규 화보 발견→다운로드(허용된 범위)→검증→클라우드 업로드→카탈로그 갱신이 실제 실행되며 실패는 사용자에게 구체적으로 드러난다.
6. 비용, 파일당 한도, 인증 갱신, 서비스 약관, 데이터 내보내기, 독립 백업 위험을 검토했고, 사용자가 승인하지 않은 비용/계정/배포를 생성하지 않았다.

## 7. 금지 및 운영 지침

- 사용자에게 비밀번호·세션 쿠키를 채팅에 붙여넣게 하지 않는다.
- 사용자 메시지를 삭제/수정했다고 단정하지 말 것. 이전에 항의 메시지 누락을 겪은 상황이므로 진행 보고는 변경된 파일·SHA·QA 로그와 일치시킨다.
- TinyFish는 사용하지 않는 것이 기본. 이미 사용자 요청으로 의존 중단.
- 개인 SNS 다운로드 건수를 사진 화보 전체 취합 성과로 보고하지 않는다.
- 8개/16개 미리보기 이미지나 단지 53개 폴더를 '아카이브 완료'로 표현하지 않는다.
- 무단 재게시 추정만으로 저작권이 없다고 처리하지 않는다. 공식 원본과 제3자 사본의 권한·품질을 구분한다.
- 문제가 발생했다고 임의 중단 선언하지 말고 관측 증거→원인 분석→대체 도구/구조→재실행→실제 수락 검증 순서로 처리한다.

## 8. 다음 개발 대화에 붙여넣을 업무 지시

이 파일을 단일 개발 인수인계서로 사용하라. 기존 코드를 초기화하거나 또 빈 아카이브를 만들지 마라. 첫 업무는 GitHub koith/browser-app-lab의 apps/yui-gallery에서 실제 5작품 405장 공개 웹판 ZIP 및 cloud/ 코드를 확인하고, 저장소 후보 하나에 안전한 실계정 연결(사용자 승인이 필요한 인증은 명시적으로 요청)→실파일 업로드→원격 해시 검증→갤러리 iPhone 수락 테스트까지 완료하는 것이다. 다음으로 중국 사이트/발행사의 나머지 모든 화보를 작품 단위로 탐색·수집하고, 발행사 원본 고해상도 획득 가능성을 검증하라. SNS 수집 실적은 제외하라. TinyFish는 사용하지 말고 GitHub Actions/Playwright/gallery-dl/Scrapy/직접 HTTP를 활용하라. 결과 보고에는 작품별 표기 장수/실보관 장수/해상도/실제 저장 위치/실QA 상태를 명시하고, 미완료는 미완료라고 보고하라.
