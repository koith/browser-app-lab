# 4LEAF 복원 개발: 완료 중심 운영 규칙 (2026-11-18)

## 왜 느렸는가 — 실제 저장소 근거

- 기존 원장 60건 중 **44 done / 15 in_progress / 1 todo**. "진행 중" 15개는 집중 개발이 아니라 장기간 분산된 누적 상태다.
- 이력 이벤트 486개와 58만 자대 원장을 반복해서 읽고 덧붙였다. 현재는 `RESTORATION_ACTIVE.json`으로 미완료 작업만 조회 가능하므로 **더 이상 전체 이력을 매번 로드하지 않는다**.
- 사용자 피드백 전에 임시 UI를 만들었다가 원작과 다름을 발견해 다시 고쳤다. 특히 **2002 PAK / 2004 화면 / 이후 리뉴얼 자료**를 서로 다른 버전으로 분리하지 않으면 배치·화면 전환·룰의 재작업이 발생한다.
- PR·패치·테스트 성공을 원작 일감 완료와 혼동했다. M02는 메인 `beta.95`가 병합됐을 때 공개 Pages가 `beta.94`인 기간이 실제로 있었고, 재검사 run 44069077562에서 공개 JS/CSS 바이트 일치까지 확인하고서야 배포가 입증됐다.
- 모바일 공통 레이아웃처럼 원본의 화면별 규격이 다른데도 한 번에 확대·축소해서 발생한 재작업이 있었다.

## 작업 방법 (예외 없는 기본값)

1. **WIP=1.** 새 작업은 `DELIVERY_FOCUS.json.activeFocus` 하나만 최종 완료 대상으로 한다. 다른 부분의 임시 최적화·우회 리팩터링·새 계측 도구를 끼워 넣지 않는다. 다만 해당 일감을 완성하는 데 필요한 공유 코드·원본 추출은 같은 묶음으로 고친다.
2. **원작 두 계열을 먼저 같은 상태에서 대조.** (A) 2002–2004 원본 클라이언트·PAK·CHR·DMP·당시 캡처 (B) 이후 리뉴얼판의 화면·동작 증거. 둘이 다르면 버전별로 표기하고, 무조건 리뉴얼판을 원작이라 취급하지 않는다. (C) 현행 웹앱과 세 번째 비교를 한다. 실제 확보 못한 근거는 `UNVERIFIED`로 적고 가상 재현을 원본처럼 표시하지 않는다.
3. **한 업무를 세로로 완성.** 화면 진입, 정확한 자원·레이아웃, 모든 버튼·게임 사이클, 실패/재접속, 모바일 가로/데스크톱 입력까지 한 작업의 범위에 넣는다. "절반만 구현한 뒤 나중에 연결" 방식 금지.
4. **한 번에 수정·검증.** 개발 중에는 필요한 가장 작은 테스트만 실행한다. 원작 화면·전체 흐름을 다 구현한 뒤 Chromium/WebKit 같은 상태 스크린샷과 실제 클릭을 수행한다. CI 수십 개와 중간 PR은 목표가 아니다.
5. **GitHub main → 공개 Pages → 기존 일감 done.** PR 생성이나 병합을 완료로 세지 않는다. 공개 URL의 실제 버전과 변경된 리소스(JS/CSS/이미지)가 main과 일치해야 한다. 플랫폼 배포 지연은 게임 문제와 분리해서 해결한다.
6. **수용 증거는 최소한만.** `DELIVERY_CLOSURES.json`에는 원본 근거, 리뉴얼 근거(없으면 조사 결과), 동일 상태 비교, 구현 커밋, Chromium·WebKit 검증, 공개 배포 검증, 완결된 사용자 흐름만 기록한다. 과거 원장 event를 무제한 추가하지 않는다. 새 done은 `check_restoration_delivery.py`를 통과해야 한다.
7. **다음 우선순위.** `P0-CHAT`을 첫 번째 단일 완료 대상으로 고정한다. 채팅 타운→원작 방 지도→방 생성→입장→채팅→퇴장→재입장을 한 번에 재현한다. 이후 순서는 `DELIVERY_FOCUS.json.nextFocus`이고, 서로 연관된 보드/주사위/전투 과제는 필요한 경우 같은 코드 변경에 묶되 원장 완료는 각 수용 기준별로 따로 판정한다.
